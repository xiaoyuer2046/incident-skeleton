# Incident Skeleton 技术说明

> 面向：开发者、要把它接入公司环境的工程师。功能概览见 [系统说明.md](系统说明.md)。
> 所有路径相对于仓库根目录。运行环境：Python 3（只用标准库）、`ping` / `curl`，可选 `snmpget`。前端为纯 HTML/CSS/JS，无构建步骤。

## 3. 数据模型

### 3.1 动作（`actions.json`）

```json
"clear-queue": {"device": "printer", "risk": "low", "zh": "清空卡住的打印任务",
                "en": "Clear stuck print jobs", "command": ["cancel", "-a", "-h", "{target}"]}
```

- `risk`：`low` / `medium` / `high`，决定权限等级。
- `physical: true`：需要人到场，永远不自动执行。
- `command`：真实执行的命令，`{target}` 替换为主机名。目前只有 `clear-queue` 配了命令，其余为 `null`，表示需要接集成。

### 3.2 处理手册（`runbooks.json`）

`设备 → 症状 → [动作…]`，顺序即"先软后硬"的默认顺序。症状由 `remediate.symptom_key()` 用关键词从告警消息中归类：

| 设备 | 症状键 |
|---|---|
| printer | `jam`、`offline`、`generic` |
| signage | `down`、`generic` |
| av | `hung`、`generic` |
| wifiap | `offline`、`generic` |

### 3.3 运行数据（`skill/remediation/data/`）

| 文件 | 内容 |
|---|---|
| `attempts.jsonl` | 每次执行：时间、设备、症状、动作、权限等级、是否恢复、`recheck_due`、`confirmed`、`regressed` |
| `audit.jsonl` | 每个决定：执行 / 需批准 / 复查，及批准人 |
| `case_history.jsonl` | 每次故障的结果摘要 |
| `case_library.json` | 病例库条目与被拦截来源 |
| `tickets.json` | 工单（`tickets`）与键索引（`by_key`） |
| `board.json` | 大面积故障进展面板 |
| `outbox.jsonl` | 通知发件箱（每条 × 每个频道） |
| `notify_state.json` | 通知去重的时间戳 |
| `alerts.log` | 人类可读的失败告警 |
| `brain_audit.jsonl` | AI 调用审计（不含内容） |
| `STOP` | 存在即紧急开关开启（含按下的人和时间） |

## 4. 一轮巡检（`orchestrator.run_cycle`）

输入：设备列表 `{id, type, upstream?, target?}`、每台的探测结果、故障描述、批准记录、维护窗口。

1. **分类** `classify(probes, need)`：
   - 失败 0 次 → `healthy`
   - 失败 < `need`（2）→ `blip`
   - 失败 ≥ `need` 且最后一次成功 → `self_healed`
   - 否则 → `confirmed`
2. **维护窗口**：非正常且在窗口内 → `maintenance`。
3. **复查** `remediate.recheck(ctx, statuses)`：处理到期的临时成功（见 §5.6）。
4. **批量合并**：同一 `upstream` 下 `confirmed` 数 ≥ `blast_radius.min_devices`（3）→ 全部改为 `upstream`，用键 `upstream|<交换机>|down` 开 / 追加一张上游单，不逐台修。
5. **主动盯盘** `watch.poll`：返回进展面板和修法提示 `hints[设备][动作] = 总单号`。
6. **逐台修复**：对每台 `confirmed` 调用 `remediate.remediate(..., hints=...)`。
7. **上游自动关单**：上游单下所有设备都已正常（或本轮已修好）→ 关单。
8. `watch.after`：记录自动化动作、回写进度、更新面板状态。
9. `notify.run`：构建并发送通知。

返回：`rows`、`events`、`results`、`board`、`rechecks`、`notifications`。

## 5. 修复闭环（`remediate.remediate`）

### 5.1 候选修法来源

| 来源标签 | 来自 |
|---|---|
| `builtin` | 处理手册 |
| `lib` | 病例库中状态为 `verified` 且能对上动作的条目 |
| `ai` | `brain.ask("suggest_actions")` |
| `master` | 总单里提到的修法（`hints`） |

同一动作合并来源。只保留 `actions.json` 中属于该设备的动作。

### 5.2 排序

排序键（越小越先）：

```
(是否到场, 风险等级 low<medium<high, 是否来自总单 0/1, -得分, 手册中的位置)
```

得分为拉普拉斯平滑的成功率，病例库作为先验：

```
score = (本地成功 + 1 + v) / (本地尝试 + 2 + v + c)
v = min(病例库验证次数, 3)，c = min(病例库无效次数, 3)
```

### 5.3 状态

| 状态 | 条件 |
|---|---|
| `demoted` | 本地尝试 ≥ 3 且成功率 ≤ 0.2 |
| `builtin` | 来源含处理手册 |
| `promoted` | 成功 ≥ 2 且成功率 ≥ 0.67 |
| `candidate` | 其余（学来但没在本地证明） |

### 5.4 决定（`decide`），按顺序

1. `physical` → `needs_human`
2. `demoted` → 跳过
3. 不在 `policy.allow[设备]` → `denied`
4. 紧急开关开启 → `killed`；今天对该设备已执行 ≥ `max_repairs_per_device_per_day`（6）→ `rate_limited`
5. 30 分钟内对该设备试过 → `cooldown`
6. 权限等级 = `policy.autonomy[风险]`；若为 `candidate` 且风险不是 `low` → 强制 `approval`
7. `approval` 且没有批准记录 → 记入"需批准"，不执行

每次故障最多执行 `max_attempts_per_incident`（4）个动作。`notify_then_act` 先通知再执行（等待 `notify_wait_seconds`）。

### 5.5 执行与验证

- 演练模式：不执行，返回 `[dry-run]`。
- 真实模式：只有配了 `command` 的动作能执行；其余返回"没有执行器"，交给人。
- 验证：演示用场景集合；真实运行时重新 ping / curl 设备。

### 5.6 延迟复查

修好的那条执行记录写入 `recheck_due = 现在 + recheck_minutes`（10 分钟）、`confirmed = null`。之后每轮巡检：

| 到期时设备状态 | 处理 |
|---|---|
| `healthy` | `confirmed = true`（稳住了） |
| `confirmed` 或 `self_healed` | `confirmed = false`、`verified = false`、`regressed = true`（这次修复改记失败，成功率随之下降） |
| 其他（维护、上游、未知） | 下轮再看 |

### 5.7 学习

`stats()` 只统计 `outcome = ran` 且已验证的记录。成功率进入排序得分，触发晋升与降级。这是统计，不是模型训练。

## 6. 工单生命周期（ServiceNow）

工单键：`<设备类型>|<CI>|<症状>`，上游单为 `upstream|<交换机>|down`。

| 情况 | 动作 |
|---|---|
| 该键有未关单（New / In Progress / On Hold） | 追加工作备注，不重复开单 |
| 该键已解决，且在 `reopen_hours`（72）内 | 重开，`reopen_count + 1` |
| 其他 | 新开单 |
| 有动作等批准 | 状态 `On Hold`，原因"等待批准" |
| 自动修好 | 以 `Solved (Permanently)` 解决 |
| 找到总单 | 设置 `parent_incident`，追加关联备注 |

开单字段：`short_description`、`description`（症状、可能原因、已做、未做）、`cmdb_ci`、`assignment_group`（按 `policy.escalation.groups`）、`category`、`impact`、`urgency`、`priority`。工作备注里附上：已做、未做及原因、冷却跳过、等批准、病例库参考、AI 诊断、紧急开关信息。

**真实同步**（`sn_sync`）：需同时满足真实模式、`escalation.dry_run = false`、设置了 `SN_INSTANCE` / `SN_USER` / `SN_PASSWORD`。新单 `POST /api/now/table/incident`，之后 `PATCH /api/now/table/incident/<sys_id>` 写 `work_notes`，解决时设 `state = 6`、`close_code`、`close_notes`。**这部分没有连真实实例测试过。**

## 7. 病例库收集（`harvest.py`）

### 7.1 来源与判定

| 来源 | verified | failed | unverified | 跳过 |
|---|---|---|---|---|
| ServiceNow KB | 已发布且有用票 ≥ 3 | — | 已发布、票数不足 | 草稿 |
| 历史工单 | 关闭代码 `Solved (Permanently)` | 关闭后复发 | 其他关闭代码 | 未解决 |
| 我们的已结工单 | 同上（工程师结单，不含自动化结单） | 同上 | 同上 | — |
| 群聊（Teams / Slack / 企业微信） | 提问人后续回复肯定，或 👍 ≥ 3 | 提问人后续回复否定 | 无确认 | 不像修法的消息 |
| 邮件 | 同群聊 | 同群聊 | 同群聊 | 同群聊 |
| 公盘（`.md` / `.txt`） | 文档头 `Status: Approved` | — | 其他状态 | 不像步骤的段落 |

- 只看"别人回复给提问人"的消息。
- 提问人确认的是同一回复里的另一个步骤 → 本动作记为 `unverified`。
- 症状由"提问 + 回复"一起归类。

### 7.2 映射到动作

先用关键词表（中英文）映射到动作；映射不上且像修法时，调用 `brain.ask("map_fix_text")`，只允许选该设备的非到场动作。

### 7.3 拦截

| 原因码 | 规则 |
|---|---|
| `override` | "ignore … rules/instructions"、"忽略…规则/指令" |
| `pipe_shell` | `curl` / `wget` 管道到 `sh` |
| `destructive` | `rm -rf` |
| `disable_safeguard` | 关闭 / 跳过 审批、权限、审计 |
| `credential` | `password:`、`密码：` |

被拦截的消息只存入 `rejected`，不参与任何决定。

### 7.4 条目

键：`设备|症状|动作`（对不上动作时为 `advice:<文本指纹>`）。`kind = auto`（可自动）或 `engineer`（到场或对不上动作）。状态：验证次数 > 无效次数 → `verified`；有无效 → `contradicted`；否则 `unverified`。

真实 KB 读取：真实模式且设置了 ServiceNow 凭据时，`GET /api/now/table/kb_knowledge?sysparm_query=workflow_state=published`。**未测试。** 群聊、邮件、公盘的真实连接器**没有实现**。

## 8. 大面积故障盯盘（`watch.py`）

每个上游单对应一个面板（`board.json`），字段：`upstream`、`our_ticket`、`devices`、`master`、`timeline`、`solutions`、`posted`、`status`、`summary`。

`poll`（修复前）：
- 匹配总单：`ci == 交换机` 或 `affected` 与我们的设备有交集。
- 首次匹配：给我们的单设 `parent_incident`，时间线记"已关联"。
- 总单新备注进时间线；备注里能对上的非到场动作 → `solutions(kind=auto)` 和 `hints`；备注的 `engineer` 字段 → `solutions(kind=engineer)`。
- 故障邮件：正文含交换机名或主题含总单号 → 进时间线。

`after`（修复后）：
- 记录本轮对面板设备的自动化结果。
- 健康数变化时，把进度写回总单（`posted`）。
- 状态：全部正常且总单已解决 → `closed`；全部正常但总单未关 → `recovering`；否则 `open`。
- 摘要：先生成模板，再交给 `brain.ask("summarize_outage_board")` 改写，失败用模板。

真实轮询（ServiceNow 重大事件、邮箱）**没有接**，目前读 `sources/servicenow_major.json` 和 `sources/outage_mail.json`。

## 9. 通知（`notify.py`）

| kind | 触发 |
|---|---|
| `outage` | 新开上游单 |
| `board` | 面板有新的总单备注、故障邮件或关联 |
| `board_closed` | 面板关闭 |
| `failed` | 修复失败并新开或重开工单 |
| `approval` | 有动作等批准 |
| `fixed` | 自动修好并关闭工单 |
| `regressed` | 复查发现修复没稳住 |
| `kill` | 紧急开关导致没修 |

- 只在工单"新开 / 重开"时报失败，追加备注不再推送。面板只推送上次之后的新条目（`notify_state.last_ts`）。
- 路由：`policy.notify.channels[].kinds`，`"*"` 为全部。
- 发送：演练写 `outbox.jsonl`；`notify.dry_run = false`、真实模式且设置了 webhook 环境变量时，`POST {"text": 英文 + 换行 + 中文}`。**真实 webhook 未测试。**

## 10. AI 接口（`brain.py`）

| 任务 | 输入要点 | 输出 |
|---|---|---|
| `suggest_actions` | 证据、允许的动作 | `{"suggestions":[{"action_id","why"}]}` |
| `map_fix_text` | 设备、文本、允许的动作 | `{"actions":[…],"engineer_only":bool}` |
| `diagnose` | 证据、已试、留给人的步骤 | `{"cause":{en,zh},"next":{en,zh},"confidence"}` |
| `summarize_outage_board` | 面板摘要、模板草稿 | `{"summary":{en,zh}}` |

保护规则（在代码里强制）：
1. 只接受 `allowed_actions` 里的 id，最多 3 个。
2. 不能改变权限：AI 选的动作照样走 §5.4。
3. KB、群聊、邮件、工单文本放在 `<data>` 标签里，系统提示说明那只是数据。
4. 必须是 JSON；文字截断到 400 字符；不合格直接丢弃。
5. 异常、超时、超出 `BRAIN_MAX_CALLS`（默认 40）→ 返回 `None`，引擎用规则。
6. 每次调用写 `brain_audit.jsonl`（任务、后端、成败、耗时、内容哈希，不含内容）。
7. 相同请求走缓存。

| `BRAIN` | 后端 | 状态 |
|---|---|---|
| `off` | 不用 AI（默认） | ✅ |
| `mock` | 确定性替身，演示用，**不是模型** | ✅ |
| `cmd` | `INCIDENT_AI_CMD` 指定的命令，stdin 请求、stdout JSON | ✅ 有测试 |
| `claude` | 本机 `claude -p --output-format json`（花 Claude 额度） | ⚠️ 未测 |
| `http` | OpenAI 兼容接口：`BRAIN_URL`、`BRAIN_MODEL`、`BRAIN_API_KEY` | ⚠️ 未测 |

## 10a. 未关单追踪（`tracker.py`）

对每张未关的设备工单（上游单由进展面板负责）：用单号、CI 和 CI 后缀（如 `2F-201`）在群聊和邮件中匹配消息，跳过夹带指令的消息；合并人工工作备注，按时间排序。从中提取预计时间（`ETA / 预计 / ships by / by HH:MM`）、在等什么（`waiting for … / 等待… / RMA`）、负责人，生成中英文摘要，可经 `brain.ask("summarize_ticket")` 改写。有新的人工信息时，以 `status_summary` 备注写回工单，不改变工单状态。公盘读取 `INCIDENT_SHARED_DRIVE`（默认示例目录）下的 `.md` / `.txt`，按空行分段映射动作。

## 10b. 会前体检、KB 草稿、聊天（`premeeting.py` / `kbdraft.py` / `chatops.py`）

- **会前体检**：每轮巡检后，对 `0 ≤ 开始时间 − 现在 ≤ premeeting.lead_minutes`（30）的会议，按房间本轮状态判定 `ready` / `fixed` / `at_risk`。`at_risk` 时选 `type = av`、本轮正常、该时段没被预订的房间作备选；`≤ move_minutes`（15）时动作为 `move`。状态变化时把工单提为 `2 - High`、紧急度 1，并发通知（`meeting_risk` / `room_move` / `meeting_saved` / `meeting_ok_again`）到"会议组织者（私信）"频道。
- **KB 草稿**：按 `设备|症状|动作` 汇总 `attempts.jsonl`。`confirmed = true` 次数 ≥ `kb_draft.min_confirmed`（2）且成功率 ≥ `min_rate`（0.5）时起草一次，写入 `kb_drafts.json`；同设备同症状、尝试 ≥ 2 且成功率 ≤ 0.34 的修法列入"不用试"。可经 `brain.ask("draft_kb")` 改写。
- **聊天**：`chatops.handle(ctx, 发送人, 文本)` 识别 `status` / `approve` / `stop` / `resume`，从不把文本当命令执行。批准要求发送人在 `chatops.approvers[设备类型]` 或 `*` 中；写入 `approvals.json[设备]`，下一轮只对该设备生效，执行后删除。回复先用模板，再经 `brain.ask("answer_chat")` 改写。巡检把最新状态写到 `last_patrol.json` 供它读取。

## 10c. 应用 2：服务台（`skill/apps/servicedesk/`）

- `remediate.Ctx(data_dir, ..., app_dir=APP)`：从应用文件夹读 `actions.json`、`runbooks.json`、`policy.json` 和 `sources/`。`app_dir=None` 是应用 1。`harvest.harvest()` 用 `ctx.sources_dir`。
- `app.json`：每个班底的 `keywords`（分诊）、`symptoms`（加入共享的 `rm.SYMPTOMS`）、`checks`（声明式排查：`path` + `eq`/`gte`/`lte`，在 `data/directory.json` 上求值）；`never_automate` 管理员类词。
- `desk.handle(ctx, office, req, directory)`：分诊顺序：① `harvest.injection_reason` 或 `never_automate` → 拒绝，转 Security；② `chatops.find_devices` / `floor_of` + 应用 1 的工单和 `board.json` → 挂单（`parent_incident`，On Hold）；③ 关键词选班底 → 声明式排查 → `remediate.remediate(..., evidence=...)`。
- `desk.close_linked(ctx, office)`：父单已解决或盯盘关闭 → 关闭挂着的请求并通知员工。
- `desk.run(ctx, office, prev_ts)`：一轮：新请求 + 关闭挂单 + `notify.send`。`simulate.py` 每轮巡检后调用一次，用同一个时钟；工单号从 INC0020001 开始。
- 命令行：`python3 skill/apps/servicedesk/desk.py --from amy --say "..." --lang zh [--works all|none|id,id]`（演练，`--works` 指定哪些动作算有效）。
- 测试：`skill/tests/test_servicedesk.py`。

## 14. 演示是怎么生成的

`simulate.py` 用一个可控的时钟（2026-11-21 09:00 起，每轮 +10 分钟）跑 14 轮 `orchestrator.run_cycle`。

- **写好的部分**：13 台设备及各自的上游交换机、每轮哪台故障、哪个动作真能修好（场景集合）、探测结果、维护窗口、工程师接单 / 结单、谁批准、何时按紧急开关，以及示例数据源。
- **引擎决定的部分**：分类、静默、合并、收集与判定、排序、权限、冷却、学习、复查、工单、盯盘、通知。
- 场景标签由 `detect_tags()` 从引擎结果中**检测**出来，不是写死的。当前覆盖 47 / 47（应用 1 的 41 个 + 服务台 hd_* 6 个）。
- 输出 `demo/data/sim.js`（`window.SIM`）：设备、动作目录、策略摘要、每轮结果、工单（含模拟总单）、病例库。两个页面只读这个文件回放。

## 16. 安全设计

- **默认演练**：设备、ServiceNow、通知三处各有独立的 dry-run 开关。
- **权限集中**：所有授权在 `policy.json`，代码不绕过。
- **最小执行面**：只有配了 `command` 的动作能真执行；到场步骤永不自动。
- **人在环中**：中风险先通知，高风险与未证明的学来修法需批准；批准人记入审计。
- **刹车**：紧急开关、冷却、每日上限、每次故障动作上限、批量合并时暂停逐台修复。
- **不可信输入**：KB、群聊、邮件、工单文本只当数据；夹带指令的消息被拦截；AI 只能从目录里选动作。
- **可追溯**：每次执行、决定、复查、AI 调用、通知都有记录。
- **凭据**：只从环境变量读取，建议由密钥库注入，并使用最小权限的服务账号。

## 18. 已知限制

- 症状归类和群聊判定靠关键词，复杂语句可能判错（接真 AI 后可改善）。
- 延迟复查能发现"没稳住"，但不能区分"本来就会自愈"和"修好了"；自愈规则只覆盖探测期间就恢复的情况。
- 进展面板一次只展示第一个上游故障。
- 工单"描述"字段只写英文。
- 学习按"设备类型 + 症状 + 动作"统计，不区分具体型号。
