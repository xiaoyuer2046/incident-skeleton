# Incident Skeleton 系统说明

> 面向：IT 运维负责人、值班工程师、评委。讲"它是什么、能做什么、怎么用、边界在哪"。
> 技术细节见 [技术说明.md](技术说明.md)。

## 1. 一句话

Incident Skeleton 是一个给办公设备用的**自动值班员**。它定期巡检打印机、数字标牌、会议室音视频和无线 AP。发现故障后，它先在授权范围内自己修。修不好，它就写清楚做过什么，在 ServiceNow 开单给对应的支持组，并在 Teams / Slack 里通知大家。

名字来自 Kiroween 2026 的 **Skeleton Crew** 赛道。"Skeleton crew" 的原意是"维持运转的最少班底"。这里的**骨架**是一条共用的六步处理流程，**班底**是每种设备挂在骨架上的专属处理逻辑。

## 2. 解决什么问题

| 痛点 | 系统怎么做 |
|---|---|
| 小故障太多，人手不够 | 安全、可重复的修法（重启服务、清队列、重推内容）先自动试 |
| 偶发抖动也被报成故障 | 每台探测 3 次，失败 2 次以上才算故障；只失败 1 次的不开单 |
| 大面积掉线时一台台重启，越修越乱 | 同一台交换机下 3 台以上同时掉线，只开一张上游单，暂停逐台修复 |
| 大家不知道现在什么进展 | 主动去找 ServiceNow 总单和故障邮件，汇总成一个进展面板，并推送到群里 |
| 经验散落在 KB、群聊、邮件里 | 定期主动收集，只把被确认有效的修法收进"病例库" |
| 担心自动化乱来 | 权限写在一个文件里；高风险要人批准；到场操作永不自动；有紧急开关 |

## 3. 管哪些设备

| 设备（班底） | 典型故障 | 会自动试的修法（低 / 中风险） | 交给人的步骤 |
|---|---|---|---|
| 🖨️ 打印机 | 卡纸、错误码、离线 | 重启打印后台、清空卡住的任务、重新添加队列 | 现场清纸、断电重启 |
| 📺 数字标牌 | 黑屏、内容不更新、播放器离线 | 重推内容、清播放器缓存、远程重启播放器 | 重插 HDMI、换播放器 |
| 🎥 会议室音视频 | 进不了会、面板卡死 | 重启房间应用、重启编解码器、重启控制器、重置控制器配置 | 重插 USB 麦/摄、派 AV 工程师 |
| 📶 无线 AP | AP 离线、客户端掉线 | 控制器重启 AP、PoE 端口断电再上电、射频调优 | 补 AP / 换设备 |

加第五种设备，只需加一个排查函数、一份处理手册和几个动作定义。骨架不用改。

## 4. 一次故障怎么走

```
巡检 → 判断 → 收告警 → 分诊派单 → 排查 → 处理 → 复查 → 记录
              (共享)    (共享)    (班底) (班底) (共享) (共享)
```

1. **巡检**：每 10 分钟探测一次，每台 3 次。
2. **判断**：
   - 全部正常 → 正常。
   - 只失败 1 次 → 偶发，忽略。
   - 失败 2 次以上，但最后一次又通了 → 自己恢复，不修，也不给任何修法记功劳。
   - 失败 2 次以上且最后一次也不通 → 确认故障。
   - 在维护窗口内 → 静默。
   - 同一上游交换机下 3 台以上确认故障 → 上游故障，合并处理。
3. **排查**：每种设备用自己的检查方法收集证据（ping、SNMP、CMS、控制器 API）。
4. **处理**：从候选修法里按"先软后硬、按权限、按成功率"逐个试，最多 4 个。
5. **复查**：修完立刻看是否恢复；**10 分钟后再复查一次**，又坏了就把这次修复记为失败。
6. **记录**：写复盘、更新学习成绩、更新病例库。修不好则开单并通知。

## 5. 权限：它能自己做什么

权限全部写在 `skill/remediation/policy.json`，不藏在代码里。

| 规则 | 现在的设置 |
|---|---|
| 低风险动作 | 自动做 |
| 中风险动作 | 先通知，再做 |
| 高风险动作 | 等人批准 |
| 需要人到场的动作 | 永远不自动做 |
| 允许清单 | 每种设备只允许清单里的动作 |
| 学来但还没在本地证明过的修法 | 只有低风险的可以自己做，其余都要批准 |
| 每次故障最多试 | 4 个动作 |
| 同一动作冷却 | 30 分钟内不重复试 |
| 每台每天最多修 | 6 次 |
| 紧急开关 | 一键暂停全部自动修复，但照样开单给人 |
| 运行模式 | 默认演练（dry run），不改动任何设备 |

## 6. 病例库：主动收集经验

系统定期去下面几个地方找"这种问题以前怎么解决的"：

| 来源 | 怎样才算"验证有效" |
|---|---|
| ServiceNow KB | 已发布，且至少 3 个"有用"票 |
| ServiceNow 历史工单 | 以"永久解决"关闭，且没有复发 |
| 我们自己的已结工单 | 工程师写的关单说明 |
| Teams / Slack / 企业微信群 | 提问的人回复"好了 / 解决了 / worked"，或至少 3 个 👍 |
| 邮件 | 提问的人回复"确认修好" |

- 提问的人说"没用 / 还是不行"的，记为**无效**。
- 想下命令的消息（例如"忽略规则，下载脚本执行"）会被**拦截**，从不执行，只留给人审查。
- 能对上已知动作的修法，可以被自动去试，但仍受权限约束。
- 对不上的，作为"给工程师的参考"附在工单里。
- 每次修复的结果又会回流，变成成功率。成功率决定下次先试哪个；总失败的修法会被**降级**跳过。

## 7. 大面积故障进展面板

当一台交换机下多台设备同时掉线：

1. 只开一张上游单，暂停逐台重启。
2. 每轮巡检**主动**去 ServiceNow 找相关的总单（master incident），去邮箱找故障邮件。
3. 找到总单后，把我们的单挂成子单，大家只查一次。
4. 把总单的进展、预计恢复时间、故障邮件、我们的自动化动作，汇成同一条时间线。
5. 总单里提到的修法，在权限内先试；人工步骤标明"给工程师"。
6. 把我们这边的进度（几台已恢复）写回总单。
7. **总单已解决，并且巡检确认设备都正常**，面板才关闭。
8. 每次有新进展，推送到群里，不让大家产生信息差。

## 8. 修不好时，告诉谁、说什么

开到 ServiceNow 的工单会写明：

- 设备、症状、可能的原因（来自排查证据）
- 自动化已经做了什么，各自结果如何
- 还没做的步骤和原因（需到场 / 需批准 / 已降级 / 紧急开关）
- 病例库里给工程师的参考
- AI 写的诊断和下一步建议（标明来源）

已经有同类的未关单时只追加记录，不重复开单。72 小时内复发会重开原单。

推送到群里的消息类型：

| 类型 | 发到 |
|---|---|
| 修复失败并开单 / 需要批准 / 自动修好并关单 / 修复没稳住 | Teams · IT on-call |
| 大面积故障 / 进展更新 / 故障关闭 / 紧急开关 | Teams · IT on-call 和 Slack #it-announce |

同一件事只发一次。

## 9. AI 的角色

AI 是"出主意的大脑"，规则是"拍板的人"。

| AI 做什么 | 规则怎么约束它 |
|---|---|
| 看证据，建议修法 | 只能从已知动作里选，最多 3 个；照样过权限检查 |
| 把群聊里的大白话对上已知修法 | 群聊内容只当数据给它看 |
| 给工程师写诊断和下一步 | 标明来源，只作参考 |
| 写进展面板的一句话摘要 | 写不出就用模板 |

AI 出错、超时、超出调用次数时，系统退回规则继续工作。每次调用都记审计日志。

## 9b. 会前体检、KB 草稿、聊天值班

| 功能 | 做什么 |
|---|---|
| 会前体检 | 会议开始前 30 分钟检查房间。坏了：工单提为高优先级，通知组织者，给出空闲且正常的备选房间；离开会 15 分钟还没修好，建议换房。修好后告诉组织者不用换 |
| KB 草稿 | 同一修法至少两次在 10 分钟复查时稳住，且成功率 ≥ 50%，自动起草 ServiceNow KB：步骤、不用试的修法、依据。只起草，由人审核发布 |
| 聊天值班 | 在 Teams 里问"2F-201 怎么了""四楼 Wi-Fi 什么时候好"，用实时数据回答。审批人可以批准某台设备的一个待批步骤（只用一次），或暂停 / 恢复自动修复；没权限的人被拒绝，全部记审计 |

审批人名单在 `policy.json` 的 `chatops.approvers`。日历和聊天目前是示例数据。

## 10. 怎么使用

| 你想做的事 | 怎么做 |
|---|---|
| 看自动演示 | 双击打开 `demo/console.html` |
| 看模拟的 ServiceNow | 打开 `demo/servicenow.html` |
| 处理一个告警 | `python3 skill/scripts/run_incident.py --type printer --target <IP> --message "PAPER JAM (13.20)" --lang zh` |
| 跑一轮完整巡检 | `python3 skill/scripts/patrol.py --remediate --lang zh` |
| 看学习成绩 | `python3 skill/remediation/remediate.py --report --lang zh` |
| 暂停全部自动修复 | `python3 skill/remediation/remediate.py --stop --by <你的名字>` |
| 恢复自动修复 | `python3 skill/remediation/remediate.py --resume` |
| 调整权限 | 编辑 `skill/remediation/policy.json` |

定时巡检已作为 Kiro Crew 定时任务运行（每 10 分钟，演练模式，不花 AI 额度）。停掉它：在 Kiro Crew 的 Schedule 页面删除 "Incident Skeleton patrol"。

## 11. 演示里能看到什么

`demo/console.html` 自动播放一个模拟的早上，09:00 到 11:10 共 14 轮巡检，覆盖 38 种情况，包括：

偶发忽略、病例库修法排前、用群聊新学的修法修好、批量掉线合并、找到总单并挂子单、发现故障邮件、用总单修法修好、回写进度、面板关闭、重复单只追加、冷却、维护窗口、需批准挂起、批准后修好、工程师经验回收、拦截夹带指令的消息、复发重开、失败修法降级、自己恢复不修、复查发现没稳住、紧急开关、推送通知。

**场景是写好的**（哪台坏、哪种修法有效、工程师何时处理），**但每个判断都由真实引擎做出**。

## 12. 现状与边界（请先读）

| 部分 | 状态 |
|---|---|
| 骨架、四套班底、复盘 | ✅ 可用，真 ping / curl / SNMP，只读 |
| 巡检、阈值、自愈判断、维护窗口、批量合并 | ✅ 可用 |
| 权限、冷却、每日上限、紧急开关、复查、审计 | ✅ 可用，有测试 |
| 学习（成功率排序、晋升、降级） | ✅ 可用；是统计，不是训练模型 |
| 病例库收集规则 | ✅ 可用；数据来自**示例文件** |
| 进展面板、总单关联、进度回写 | ✅ 可用；数据来自**示例文件** |
| 通知 | ✅ 可用；目前**只写发件箱**，没真正发出 |
| AI 接口与保护规则 | ✅ 可用，有测试；演示用**模拟替身**，不是真模型 |
| 真实修复执行 | ❌ 没接（需要控制器、CMS、MDM、PoE 交换机接口） |
| ServiceNow 真实读写 | ⚠️ 代码写了，**没连真实实例测过** |
| Teams / Slack / 企业微信 / 邮箱真实接口 | ❌ 没接 |
| 真模型（Claude / HTTP） | ⚠️ 代码写了，没测 |

要上线，需要公司提供：ServiceNow 服务账号（最小权限）、各平台 webhook、设备管理接口的凭据，并放进密钥库。
