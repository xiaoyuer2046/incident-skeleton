# Roadmap — 从被动骨架到自主 AIOps

`Incident Skeleton` 今天是**被动**的:一张告警进来,骨架把它走完六步,查出
根因,给出修复建议,写一份复盘。这是第一步——证明骨架能驱动多套班底。

真正想要的是**主动**的:系统自己发现问题、先自己修、自己找解法、追踪进度、
还越用越懂。下面是从当前形态到那个目标的几步。每一步都是在同一套骨架上加
东西,不是推倒重来——这正是"骨架"的价值。

## 今天有的(已完成)

- 一套六步状态机,四种设备班底(打印机/标牌/会议室/无线 AP)可插拔
- 真只读检查:ping / curl / SNMP
- 给出修复建议,默认不执行破坏性操作
- 每次跑完自动写一份事件复盘

## 下一步:自主 AIOps 班底

### 1. 自动检测并报警(主动,不等工单)

不再等有人提工单。系统按计划巡检:ping/SNMP 拉打印机状态、查标牌 CMS 心跳、
查会议室控制器健康、查无线 AP/控制器状态。一有漂移就生成告警,交给同一套
骨架处理。

**阈值/确认闸门 —— 不是每次抖动都开单。** 只在确认后才报警开单:

- 持续性:状态持续 > T 秒(如离线 > 60s)才算;瞬时抖动(几秒又恢复)忽略
- 频次:滑动窗口内 > N 次(如 5 分钟内 3 次)才算;偶发一次不开单
- 去重/合并:同设备同症状已有**开放工单** → 合并进现有工单(work note),不重开
- 静默:维护窗口 / 计划重启 / 更新中 不算
- 未达阈值 → 只记一条事件日志(进病例库低优先级),不惊动人

**达到阈值 → 自动开单 + 派单(ServiceNow 写面):**

- `POST /api/now/table/incident`,带 `short_description`(症状)、`cmdb_ci`(那台设备的 CI)、`urgency`
- 派单三条路,从简到 native:
  1. 设备类型→组映射直接写 `assignment_group`(打印机→打印服务组,标牌→AV/标牌组,会议室→会议室组,无线 AP→网络/无线组)
  2. 只填 `cmdb_ci`,让 ServiceNow 按 CI 的 support group / 位置自动路由(最 native,路由逻辑留在 ServiceNow)
  3. 按位置派现场 IT
- 派完 ServiceNow 按通知规则提醒该组(邮件/Slack/Teams)
- **ServiceNow 工单 = 事实记录**:后续 INVESTIGATE/MITIGATE 进展写回 work note,RESOLVE 时关单

### 2. 初步修复(能自动修的就先修)

从软到硬,四层往上试,先软后硬:

| 层 | 打印机 | 标牌 | 会议室 | 无线 AP |
|---|---|---|---|---|
| ① 软件层 | 重启 cups `systemctl restart cups`;清队列 `cancel -a` | CMS 重新推送内容/排期(API) | 重启 Zoom Rooms / Teams Rooms 应用(API/管理台) | 控制器重新下发配置 / bounce SSID |
| ② 设备层 | 打印机 Web 接口 / SNMP set 复位 | CMS/MDM(Jamf)远程重启播放器;树莓派 `ssh reboot`;屏 LAN 开机 | 编解码器重启(Cisco xAPI `xcommand Boot`/Poly REST);房间主机 MDM/Intune 重启;控制器 SSH/REST 重启 | 控制器 API 重启 AP(Meraki/Aruba/Cisco WLC) |
| ③ 电源层 | 智能插座(PDU)SNMP/REST 断电重启(兜底) | PDU 断电重启 | PDU 断电重启 | PoE 交换机端口断电再上电(`shutdown`/`no shutdown` 端口) |
| ④ 调整/任务层 | 清卡住任务 `lprm` | 强制重新同步排期 | 重启重新枚举 USB | 射频调优:换信道 / 调功率;补 AP |

- 白名单只跑**幂等、可回滚、影响面小**的操作;失败回退人工
- **分级审批**:低风险自动修;中风险"先通知值班人,超时再修";高风险(重启生产核心 / 影响多人)**等人批准**才动——不能全自动
- 不能自动修的(卡纸/换耗材/重插 HDMI/USB/硬件坏)→ 标"需人工",升级给值班人

### 3. 根据症状匹配解决方案

现在 MITIGATE 是每设备类型写死一张清单。下一步按**症状**匹配:把检测到的
症状(错误码、不通、黑屏、进不了会、大面积掉线)映射到已知解法,不只看设
备类型。同一个"不通"在打印机和标牌上解法不同,骨架按症状选。

- 症状指纹 → 解法 映射表(随病例库一起长大)

### 4. 自动搜集解决方案(没现成解法时去找)

症状没匹配到已知解法时,系统自己去**知识来源**找"这种事以前怎么解的":

- **ServiceNow KB**(读面):搜相关错误码/症状的 KB 文章
- **公司公盘**:运维文档、Runbook、设备手册
- **聊天记录**:Slack/Teams 里历史上类似问题的讨论和解决过程

找到候选解法整理成可执行步骤,交给骨架的 MITIGATE 去试。把"一个人的经验"
变成"全班的经验"。

### 5. 病例库(越用越懂的案例库)

每次事件 + 根因 + 真正生效的修复,记进一个**病例库**(case-history knowledge
base)。下次再出现相似症状,先翻病例库:以前怎么治好的、治了多久、复发没。
新解法也回流进库。第 3 步的"症状→解法"匹配,数据就来自这个库。越跑越准。

- **质量闸门**:只在修复**经确认生效**后才入库;失败/未验证的只记"尝试",不进解法库。每条解法带成功率,成功率低的自动降权或人工复核——否则库越用越脏。

### 6. 开放工单态势追踪与现状摘要

对每张**未关闭**工单,定期(或按需)从多源抓取并汇总成"现状摘要",不用人
去翻三个系统拼进度:

- **ServiceNow**:工单 work notes / comments / state / 活动日志
- **聊天**:Slack/Teams 搜工单号 / 设备名 / 关键字
- **邮件**:邮箱搜工单号 / 关键字

用模型把碎片汇总成结构化现状:已试过什么、现在什么状态、谁在跟、最近一条
更新、卡在哪。输出写回工单 work note,或推到值班人聊天频道——打开工单就能
看"现状一句话"。

## 依赖与风险(点到为止)

- **隐私/权限**:第 4、6 步抓聊天和邮件,要限范围(只相关频道和工单相关内容)、有留存和审计,不能全量扫
- **病例库存哪/怎么搜**:ServiceNow 自定义表,或向量库做语义搜;没这层,第 3 步"症状→解法"匹配落不了地
- **CMDB 干净度**:第 1 步 native 派单靠 CMDB 里设备是 CI 且 support group 准;CMDB 旧/缺,就派错组

## 为什么骨架撑得住这条路

这几步每一步都是在六步状态机**外圈加一层**,或把某一步的"写死"换成"查库
/动手"。核心骨架不变,所以从演示页到这套自主系统是同一条代码主线——"一套
骨架,多套班底"的延伸论点:骨架不光能换班底(已加到 4 套),还能从被动长成主动。

## 用 Kiro 的什么(为路线图留的钩子)

- **spec-driven**:`SPEC.md` 是骨架源头,每加一个能力先改规格
- **skill / 代理**:巡检、搜集解法、写病例库、工单现状摘要都是代理能干的活
- **MCP**:接 ServiceNow(开单/派单/查 KB/读 work notes)、公盘、邮件——把外部系统变成代理能调的工具
- **聊天/邮件集成**:Kiro Crew 已有的 Slack/Teams/邮件集成,直接用于第 4、6 步的抓取
- **memory / 知识库**:病例库本质就是会增长的知识层
